# 发布门槛与接入验证计划

## 工程门槛

首次联网安装后提交真实 lockfile；完整类型检查、标准包和演示站构建、SSR 与正式 Chrome 测试必须通过。检查生成的 .d.ts、CSS 导出、包内 LICENSE、ESM 路径和消费项目树摇结果。进行依赖与许可核查，不用“开源”代替依赖安全判断。

执行 CI 配置并保留日志。当前没有创建远程仓库、发起 CI、发布 npm 包或部署公网服务。

## 浏览器门槛

在真实目标设备记录 Chrome 完整版本、OS、CPU/GPU、显示缩放和加速状态；用固定背景集合测可读性、输入响应、滚动与弹层。只有通过的范围才写进支持合同。

目前 Vite 的 chrome120 是**构建语法目标**，不是已经验证的最低支持版本。当前唯一实测浏览器是 Linux headless Chromium 144；Windows/macOS、正式 Google Chrome 与 Android 都没有据此自动获得支持声明。

## 视觉与交互门槛

逐项检查长中文、英文、数字、200% 缩放、disabled/loading、键盘焦点、真实动态媒体、系统减少透明度与强制颜色。对比度失败直接增加底色或不透明回退，不靠文字阴影掩盖问题。

共享位置过渡不是物理材质融合。若新增合并轮廓或活动透镜融合，应重新建立共用几何和像素验证，不对整个内容层应用 blur/threshold。

## 产品验证

邀请 5–8 位目标开发者做探索性接入，不把该样本当统计代表性研究。任务一：替换现有媒体工具栏；任务二：加入菜单/设置弹层；任务三：接入一个含滚动正文的实际页面。

记录接入耗时、导入/样式冲突、被迫修改 token 数量、失败背景、键盘问题与第二页复用意愿。访谈记录模板：背景与任务、实际步骤、错误日志、修改记录、最终可用状态、放弃原因。先解决重复发生的问题，再扩展目录。

## 发布决定

只有工程、浏览器和主要交互门槛通过后，才将 alpha 变成可对外承诺的稳定版本。现有内核对照应在投入复杂自研融合之前完成；必要时继续让 CSS 做正式默认，而不是为了折射强行扩大承诺。
