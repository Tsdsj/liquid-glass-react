# Liquid Glass React 网页组件库：产品、设计与技术调研报告

## 1. 核心结论与研究边界

**建议立项，但将目标定义为“以 Apple Liquid Glass 为视觉与交互参照的 React 组件系统”，而不是“给所有组件加透明模糊背景”。**

推荐的总体方案是：

> 以真实 DOM 承载内容和交互，以 CSS 建立基础材质，以 SVG 位移滤镜增强背景折射，以无样式交互组件提供行为基础，必要时用 Motion 实现状态过渡；只针对 Google Chrome 建立明确的兼容和性能承诺。

这个方向具备公开实现依据：已有 React 项目提供背景折射效果，也已有采用 Base UI、SVG 材质内核和源码分发的完整方向性竞品。因此，技术问题不再只是“网页能不能像玻璃”，产品问题也不是“市场有没有这样的库”，而是能否提供更一致的设计、更可靠的可读性，以及可验证的工程质量。[^4][^5][^6]

### 1.1 五项关键决策

| 决策 | 建议 | 判断依据 |
| --- | --- | --- |
| 产品定位 | 导航与交互层组件系统，而非全页面玻璃皮肤 | 更贴近 Apple 对功能层与内容层的区分，也便于控制视觉复杂度。[^1] |
| 默认设计 | 克制、可读的 regular 材质；clear 作为受控场景选项 | 透明程度不能取代内容可读性。[^1] |
| 技术主线 | CSS 基础层 + SVG 背景折射增强 | 适合真实 DOM 页面，已有公开项目可作验证基线。[^4][^5][^6] |
| 交互基础 | Base UI 或 Radix 二选一，避免首版自建全部交互行为 | 两者均提供无样式交互基础，但整合后的可访问性仍需要测试。[^8][^9] |
| 首版策略 | 少量组件、完整状态、真实场景验证 | 优先证明系统可用，再扩充组件目录；这是产品建议，不是市场统计结论。 |

### 1.2 范围与证据边界

资料检索截至 **2026 年 9 月 10 日**。设计依据以可访问的 Apple Human Interface Guidelines、官方设计讲解和开发文档为主；技术依据以 Web 标准、框架官方文档及项目公开源码、README 为主。

浏览器范围仅为 **Google Chrome**。本报告以桌面端 Chrome 为主要工程基线；若 Android Chrome 也纳入首发范围，需要额外验证触控、移动 GPU、滚动与能耗。不能仅因为浏览器名称相同，就把未测试的平台视为已支持。

本报告是资料调研和架构建议，**未对候选库进行完整安装测试、逐帧视觉比较或真机性能测试**。以下不提供虚构的性能排名、市场规模、用户增长数字或“还原度百分比”。最低支持的 Chrome 版本，应在概念验证后确定，而不是凭属性名称支持情况推断。

Apple 的文档提供设计原则和原生接口，但不是可直接移植到浏览器的公开材质着色器。合理目标是视觉与行为上的近似，不是承诺网页与系统合成器逐像素相同。[^2][^3]

## 2. 产品调研：应该解决什么问题

### 2.1 目标用户与核心需求

建议将第一批目标用户定义为：希望在 React 产品中采用高品质浮动控制界面，但不愿自行处理材质、交互状态和背景可读性的开发者及产品团队。这是需要通过访谈验证的定位假设。

| 目标场景 | 适合使用玻璃的部分 | 应保持稳定、清晰的部分 |
| --- | --- | --- |
| 图片、视频、音乐类应用 | 浮动工具栏、播放控制、导航切换、音量控件 | 媒体内容、字幕、详细信息 |
| 创作与编辑工具 | 顶部操作区、悬浮操作面板、命令菜单 | 画布、时间轴、属性表单、文本编辑区 |
| 轻量工作台或个人工具 | 导航壳层、快捷操作、弹出层 | 数据表格、长列表、正文和密集表单 |
| 展示型网站 | 少量重点交互、演示控件 | 长篇文案、主要阅读区域 |

**不建议以“把后台管理系统的全部卡片、表格和输入框玻璃化”作为首个产品样板。** 在这个项目中，玻璃应该帮助识别操作层，而不是把不同层级都变成同一种半透明表面。

### 2.2 产品价值不能停留在外观

组件库应同时交付三种价值。

**视觉价值：** 不同尺寸和形状的控件共享一致的边缘、圆角、厚度与光照语言，不是每个组件各自调一套阴影。

**交互价值：** 鼠标、键盘、焦点、选中、按下和展开状态形成连续且可理解的反馈；弹层的位置与触发来源有清晰关系。

**工程价值：** 有稳定的默认值、SSR 策略、主题接口、透明度控制、降级路径和 Chrome 回归测试。接入者不需要先理解 SVG 滤镜才能得到一个可用按钮。

建议的产品描述是：

> 一套面向 React 与 Chrome 的 Liquid Glass 风格交互组件，提供可组合的材质、完整的交互语义，以及经过场景约束的视觉效果。

“可组合”和“经过场景约束”应成为实际 API 与文档规则，而不是宣传词。

## 3. 竞品与生态调研

以下比较基于公开资料。项目具备某项 API，不等于其所有边界情况都经过验证；没有在 README 中突出某项能力，也不等于它一定不存在。

| 项目或方案 | 公开定位与能力 | 适合作为什么参照 | 对新项目的启示 |
| --- | --- | --- | --- |
| `rdev/liquid-glass-react` | React 玻璃效果容器，提供折射、模糊、色散、弹性和交互相关参数。[^4] | 材质封装和效果参数参照 | “一个可调的玻璃容器”已经不是充分差异化。 |
| `shuding/liquid-glass` | 以可复制的 SVG shader 演示为核心，公开代码使用 Canvas 生成位移信息。[^5] | 小规模光学实验和实现思路参照 | 演示内核可以帮助验证折射，但组件系统还需要语义、状态与生命周期管理。 |
| Liqui Design | React 组件，基于 Base UI；通过 shadcn CLI 分发源码，使用独立玻璃内核与 SVG 折射。[^6] | 最直接的方向性竞品 | “Base UI + SVG + 源码分发”已经有实际项目，必须评估复用和差异化，而不是默认从零重做。 |
| shadcn/ui | 以可访问组件代码、组合方式和分发机制为核心的生态。[^7] | 接入体验、源码所有权和 registry 设计参照 | 可以借鉴分发方式，但不能把复制源码等同于免维护。 |
| Base UI / Radix Primitives | 无样式交互基础，提供组件行为与可访问性相关能力。[^8][^9] | 交互基础设施 | 更适合做底座，而不是作为玻璃外观竞品。 |

本次查看的 rdev、shuding 和 Liqui Design 仓库均标示 MIT 许可；实际采用时仍需锁定版本，并检查依赖、素材及各文件的许可要求。[^4][^5][^6]

### 3.1 推荐的差异化方向

**第一，建立设计约束，而不只是开放效果旋钮。** 同一种材质在图标按钮、工具栏和弹出层上，应有适合各自尺寸与内容密度的预设。默认 API 不应要求业务开发者逐个选择位移强度、色散幅度和光源位置。

**第二，把复杂背景可读性做成产品能力。** 文档明确哪些场景允许 clear，背景未知时如何处理，何时需要局部底色，何时应直接切换成不透明表面。

**第三，把性能与兼容结论做成可复现资料。** 在相同背景、相同面积和相同设备上比较效果，公开测试条件和适用范围，而不是宣称“极致流畅”。

**第四，提供完整场景。** 一套媒体工具栏和一个可实际操作的工作区，比二十张孤立组件截图更能检验交互一致性。

### 3.2 自研、复用与源码分发的选择

建议先比较现有内核，再决定自研比例。

| 路线 | 优势 | 代价 | 建议 |
| --- | --- | --- | --- |
| 复用现有玻璃内核，独立设计上层 API | 更快验证组件系统价值 | 需要接受或隔离上游约束 | 优先验证。 |
| Fork 内核并维护 | 可以控制视觉细节和修复节奏 | 需要承担更新、审计和长期维护 | 只有明确发现上游限制时采用。 |
| 从零实现材质与组件 | 控制力最高 | 光学、行为和工程风险叠加 | 不建议直接作为首步。 |
| npm 内核 + 可复制组件源码 | 内核可以集中修复，上层容易定制 | 需要维护版本对应关系和迁移说明 | 推荐作为成熟后的分发形态。 |

上述选择不是必须捆绑：完全可以先用普通 npm 组件包验证需求，再补充 registry。

## 4. 设计方向：选择“系统性还原”，而不是“装饰性模仿”

### 4.1 三种可选方向

| 方向 | 视觉特点 | 适用目标 | 主要风险 |
| --- | --- | --- | --- |
| 原生参照型 | 克制的浮动控制层、清晰几何、连贯的交互来源 | 建立视觉与交互基准 | 容易把某一张系统截图误当成所有场景的固定答案。 |
| 生产混合型 | 玻璃操作层 + 稳定内容层，按场景控制透明程度 | 实际网页产品，建议默认采用 | 演示效果不如夸张特效强烈，需要靠完整体验体现价值。 |
| 表现实验型 | 强折射、显著色散、液滴融合、鼠标光照 | Playground、创意展示 | 可读性、视觉疲劳和性能风险较大。 |

**建议以“原生参照型”做研究标尺，以“生产混合型”做默认产品，以“表现实验型”做独立实验预设。** 不要把实验效果混入所有组件默认值。

### 4.2 设计工作流

设计稿主要负责布局、尺寸、层级、状态和 token；浏览器原型负责验证动态背景下的光学与可读性。

建议建立三个固定参考场景：媒体查看器、带滚动内容的工作区、包含选择控件的交互实验台。每个新材质或新组件都放入相同场景比较，而不是临时寻找一张最能衬托效果的壁纸。

Apple 官方介绍也将材质的形变、光照与内容响应视为整体体验的一部分；因此，一张静态截图只能作为部分参照，不能代替交互验证。[^2]

## 5. Liquid Glass 的设计要点与网页转译

### 5.1 功能层与内容层分离

Apple HIG 将 Liquid Glass 主要放在浮于内容之上的导航与控制层，并建议内容层使用其他适合的材质。[^1]

落实到本项目，建议形成明确规则：工具栏可以是玻璃，工具栏下面的表格不应因此变成玻璃；侧边导航可以有材质，页面正文仍应保持稳定；一个玻璃容器内部的普通按钮，默认不再重复采样一次背景。

这不是禁止一切嵌套效果，而是避免把“玻璃套玻璃”做成无意识的默认结构。需要独立活动透镜的滑块等控件，应单独设计并验证。

### 5.2 regular 与 clear 是材质选择，不是明暗主题

| 材质 | Apple 公开指导的核心区别 | 建议的网页策略 |
| --- | --- | --- |
| `regular` | 模糊并调整背景亮度，以支持前景可读性；适用于包含较多文字的界面。 | 默认材质，配合更保守的底色与文字 token。 |
| `clear` | 更透明，适合让图片、视频等背景保持突出。 | 仅用于受控媒体场景，不作为所有组件的默认值。 |

以上是材质用途区别，不意味着 `regular = light`、`clear = dark`。[^1]

Apple 当前指导是在 clear 下方背景较亮时考虑增加约 35% 不透明度的暗化层；背景已足够暗或已有相应暗化时，不必重复添加。这不能被转译成“所有 clear 控件都固定加 35% 黑色”。[^1]

网页库应独立提供主题、材质和背景上下文三个维度。背景未知时，选择更保守的材质，比声称“自动适配所有背景”可靠。

### 5.3 光学特征：重点是边缘透镜，不是全域水波

Apple 的讲解强调 lensing、动态光照和响应交互的材质变化。[^2] 对网页实现，建议将外观拆成以下可独立控制的层；这是拟议的工程模型，不是对 Apple 私有渲染管线的复述。

| 层 | 目标 | 建议约束 |
| --- | --- | --- |
| 背景透射 | 保留背景存在感 | 不要求所有背景细节都清晰穿透。 |
| 模糊与底色 | 为文字和图标提供稳定基底 | 与内容密度关联，不只与主题关联。 |
| 边缘折射 | 表达厚度和透镜感 | 主要集中在边缘，中心区域尽量平稳。 |
| 轮廓高光 | 提示曲率与受光方向 | 有方向、强弱和衰减，避免均匀发白的粗边框。 |
| 阴影 | 表达表面与内容的空间关系 | 避免用大面积浓重阴影冒充厚玻璃。 |
| 交互变化 | 表达按下、选中和展开 | 小幅、短促、有明确触发原因。 |

不建议默认加入全表面 `feTurbulence` 水波、持续流动噪声、强烈彩虹边缘或跟随鼠标大角度倾斜。这些可以是创意风格，但不应成为本项目对 Liquid Glass 的基础定义。

### 5.4 几何：圆角必须与尺寸、嵌套和密度关联

Apple 官方区分固定圆角、胶囊和同心形状，并说明在密集桌面界面中，小型控件仍可使用圆角矩形，胶囊更适合显著操作。[^10]

因此，不建议全库统一 `border-radius: 9999px`。建议提供 compact 与 comfortable 两类密度：前者偏向桌面工具和属性面板，后者偏向导航和显著操作。

对于等距内缩的圆角矩形，可以将下面的关系作为起点：

```text
内圆角 ≈ max(0, 外圆角 - 内边距)
```

它有助于建立嵌套关系，但不是所有连续曲率、非等距内边距和复杂轮廓的通用公式。[^10]

`corner-shape` 与 superellipse 可以作为后续几何增强方向；相关标准定义了这些概念，但不能仅凭规范存在就把特定 Chrome 版本的实际渲染视为已验证，也不能把 CSS squircle 直接宣称为 Apple 连续圆角的精确复制。[^11]

### 5.5 色彩与排版：品牌色用于表达作用，不是给整页染色

Apple 的色彩指导强调让颜色服务于控制状态和重要动作，而不是无差别覆盖所有控件。[^12]

本项目建议使用中性的材质基底，将强调色主要用于主操作、选中状态和必要的状态提示。文本使用语义 token，例如主文字、辅助文字、禁用文字，不让每个组件自行选择透明黑或透明白。

优先采用系统字体栈，单独验证中文、英文、数字和长标签。不要把“看起来像 Apple”简化为“捆绑一个 Apple 字体文件”。字体分发的许可问题见第 12 节。

### 5.6 动效：表现关系和状态，不追求无处不在的弹性

Apple 的设计讲解强调表面与触发来源之间的关系，例如操作层从相关控制位置展开。[^10] 网页中可以通过锚定弹层、共享位置过渡和局部按压反馈转译这种连续性。

建议的首轮调参范围如下，**这些是本项目的起始建议，不是 Apple 官方参数**：

| 动效 | 建议起始范围 | 设计意图 |
| --- | --- | --- |
| 按下反馈 | 80–120 ms | 立即确认输入，不等材质动画结束才执行操作。 |
| 释放与短状态切换 | 180–260 ms | 保持响应感，避免明显拖尾。 |
| 相关表面的位置、尺寸过渡 | 220–360 ms | 让来源和去向容易被理解。 |

弹簧动画还需要分别设置阻尼和幅度；不能仅靠上述时长描述全部行为。默认避免文字本体明显拉伸，减少动效模式下取消弹性和追踪式高光。

### 5.7 滚动边缘：建立分界，而不是叠加更多雾层

Apple 的设计系统包含滚动边缘处理，用于让经过功能层下方的内容仍然保持合理分离。[^10]

建议将网页 `ScrollEdge` 设计为与滚动容器绑定的独立能力：只有发生内容交叠时才出现，支持浅分隔或柔和渐隐两类预设。不要让工具栏、布局容器和页面业务代码各自叠一层渐变，最后形成过厚的遮罩。

## 6. 首版组件范围与 API 方向

### 6.1 首版先完成一套可组成真实界面的组件

| 层级 | 建议组件或能力 | 首版重点 |
| --- | --- | --- |
| 全局策略 | `GlassProvider` | 主题、材质策略、渲染器、透明度和动效设置。 |
| 材质基础 | `GlassSurface`、`GlassGroup` | 独立表面与共享表面规则，不承诺原生级融合。 |
| 操作 | `GlassButton`、`GlassIconButton` | 真实 button 语义、焦点、按下、禁用、加载状态。 |
| 组合操作 | `GlassToolbar`、`GlassSegmentedControl` | 分组规则、选中反馈，以及对应的键盘行为。 |
| 导航 | `GlassNavBar` 或 `GlassTabBar` | 明确它是页面导航还是页内标签页，不混用语义。 |
| 浮层 | `GlassPopover`、`GlassMenu`、`GlassDialog` | 锚定、焦点管理、关闭行为、Portal 与层级。 |
| 配套能力 | `ScrollEdge`、主题与密度 token | 让组件可以组成完整界面。 |

滑块、开关、可融合活动透镜和复杂命令面板建议作为下一阶段重点；它们适合展示材质能力，但不应挤占基础交互和可读性的验证资源。

数据表格、复杂表单、日期选择器、树和富文本编辑器不建议首版自研。需要这些能力时，应允许应用继续使用现有组件，并与玻璃壳层共同工作。

### 6.2 接口应区分四个问题

**材质是什么、使用哪个渲染器、背景是什么、用户允许什么效果，应分别配置。**

以下只是 API 设计草案，不是已经存在的包或可直接安装的接口：

```ts
interface GlassPolicy {
  material?: "regular" | "clear";
  renderer?: "auto" | "css" | "svg";
  quality?: "balanced" | "high";
  theme?: "system" | "light" | "dark";
  transparency?: "system" | "reduced" | "opaque";
  motion?: "system" | "reduced" | "none";
}

interface GlassSurfaceOptions {
  material?: "regular" | "clear";
  backdropTone?: "light" | "dark" | "mixed";
  density?: "compact" | "comfortable";
}
```

这里的 `opaque` 是组件库的可读性与可访问性策略，不是 Apple Liquid Glass 的第三种材质。

`backdropTone` 表示业务提供的背景上下文，不保证文字自动满足对比度。`mixed` 应启用更保守的前景与底色。`renderer="auto"` 的含义应限定为选择经过验证的渲染路径，而不是浏览器自动证明所有效果正常。

使用形式可以保持简单：

```tsx
// 拟议 API：名称、props 和行为仍需在原型阶段验证。
<GlassProvider renderer="auto" transparency="system" motion="system">
  <GlassToolbar aria-label="图片操作" backdropTone="mixed">
    <GlassIconButton aria-label="放大">+</GlassIconButton>
    <GlassButton>原始尺寸</GlassButton>
    <GlassButton>下载</GlassButton>
  </GlassToolbar>
</GlassProvider>
```

默认情况下，工具栏拥有一个共享材质面；内部按钮主要改变填充、轮廓和状态，不为每个子按钮再建立完整背景滤镜。

## 7. React 与 Chrome 中的大致实现方向

### 7.1 技术路线比较

| 路线 | 能力与边界 | 工程代价 | 建议定位 |
| --- | --- | --- | --- |
| CSS `backdrop-filter` + 渐变、边框、阴影 | 可以建立模糊和表面层次；普通 blur 不提供按形状变化的空间位移。[^13][^14] | 相对较低，但大面积模糊仍需测试 | 基础渲染器与安全回退。 |
| CSS `backdrop-filter: url(...)` + SVG 位移 | 可将背景采样送入滤镜，用位移图表达透镜效果；已有 Chrome 导向的公开实现。[^4][^5][^6][^14] | 中等，需要处理滤镜边界、尺寸和浏览器合成关系 | 推荐增强主线。 |
| Canvas / WebGL / WebGPU | 适合对受控纹理、媒体或自绘场景进行精细光学处理 | 较高，还要解决页面内容如何成为输入纹理 | 不作为通用 DOM 组件库首版主线。 |

最后一条尤其重要：标准 Canvas 图像输入类型并不意味着可以直接拿任意 HTMLElement 当作实时背景纹理。常规 GPU 渲染管线擅长处理已有纹理，但不会因此自动获得浏览器已经合成好的任意 DOM 背景。[^15]

所以，“用 WebGPU 就能完美折射网页所有内容”不是本报告认可的架构前提。未核实的实验性 DOM-to-texture 能力，也不应成为首版稳定能力的依赖。

### 7.2 建议的组件内部结构

```text
交互根节点：button / nav / dialog 等
├── 材质装饰层：aria-hidden，pointer-events: none
│   ├── 背景滤镜层：CSS blur 或 SVG 折射
│   ├── 底色与局部对比度保护层
│   └── 边缘高光层
├── 前景内容层：真实文本、图标、子控件
└── 焦点指示与必要的外部阴影
```

视觉裁剪和焦点轮廓应分开处理，避免圆角裁剪同时切掉键盘焦点。装饰层不应截获点击。

**不要把扭曲滤镜直接施加到包含文字的组件根节点上。** 目标是扭曲背景，而不是让按钮标签也弯曲。Filter Effects 的背景滤镜模型与普通元素 `filter` 的输入不同，需要在实现中明确区分。[^14]

### 7.3 SVG 折射的推荐流程

建议先实现圆角矩形和胶囊两种形状，暂不支持任意路径。

```text
组件宽高、圆角与边缘参数
→ 计算到轮廓的距离与法线方向
→ 生成 RG 两通道位移图
→ 通过 feImage 提供给 SVG 滤镜
→ feDisplacementMap 对背景执行空间偏移
→ 叠加底色、轮廓高光和阴影
→ 前景文字在独立层保持清晰
```

Canvas 在这里负责生成“如何偏移”的几何图，而不是截图整个网页。这样不必在每一帧重新把 DOM 绘制到 Canvas。

`feDisplacementMap` 的规范模型可以简写为：

```text
输出(x, y) = 输入(
  x + s × (R(x, y) - 0.5),
  y + s × (G(x, y) - 0.5)
)
```

其中 R、G 是选定通道的归一化值，s 是 scale。中性值是 0.5，8 位图中约为 128；不是黑色。根据该模型，当通道范围为 0–1 时，单轴偏移范围为约 -s/2 到 +s/2，实际单位由滤镜坐标系统决定。规范同时指出存在实现差异，所以仍需实际 Chrome 图像验证。[^16]

工程上建议显式设置滤镜坐标系、输入与 `result` 名称、位移图尺寸和滤镜区域。使用按 sRGB 数值编码的位移图时，应一致处理 `color-interpolation-filters`，避免色彩空间转换改变中性值；模糊和位移所需的扩展边界也要纳入测试。[^16]

**边缘图应由几何生成，而不是默认以噪声代替。** 第一版先追求“边缘有厚度、中心不扰乱阅读”，再研究更复杂的折射剖面。

### 7.4 尺寸变化、React 生命周期与 SSR

建议将材质内核与业务组件分离。业务组件只声明形状、材质和状态，内核负责尺寸观测、滤镜注册、贴图缓存和资源释放。

位移图的缓存键可包含宽高、圆角、边缘剖面和贴图分辨率。尺寸变化时合并更新，不在每次 pointermove 或滚动事件中重新生成整张位移图；设置最大尺寸和缓存上限，避免极端布局造成无界分配。

SSR 输出应先是可读的 CSS 表面，客户端完成尺寸测量后再增强为 SVG。滤镜 ID 使用稳定的生成机制，避免 hydration 不一致或多实例冲突；React 的 `useId` 可用于相关标识生成，多根应用还应按其文档处理前缀。[^17]

实现时应验证 Strict Mode 下的重复挂载与清理，释放 observer、动画回调和不再使用的 URL。鼠标高光等高频更新优先放在 CSS 变量或动画值层，不通过整个组件树逐帧重渲染。

### 7.5 交互底座与动画库

建议在 Base UI 和 Radix 中选择一套主底座。它们能够减少重复实现焦点、键盘与状态行为的工作，但改变 DOM 结构、事件传递或 ref 后，仍须验证最终组件，而不是沿用“底座可访问，所以封装后必然可访问”的假设。[^8][^9]

Motion 可用于布局变化、共享元素位置和弹簧过渡。其 `layout`、`layoutId` 能帮助表达表面之间的连续关系，但**共享布局动画不等于玻璃材质在光学上自动融合**。[^18]

建议首版把 `GlassGroup` 定义为分组与共享表面策略。真正的融合，需要共同的几何场或合并轮廓及相应位移图，可以作为后续独立能力。不要用对整个内容做 blur/threshold 的方法，顺带破坏文字和控件边界。

### 7.6 样式与包结构建议

建议使用 React + TypeScript，样式核心采用 CSS 自定义属性，将颜色、几何和材质参数集中成 token。Tailwind 适配可以另行提供，不建议让所有接入者必须采用同一套业务样式框架。

可将工程拆成设计 token、材质内核、交互组件和文档示例四层。动画依赖保持可选，避免只使用基础按钮也需要引入全部实验效果。发布时分别测量基础组件和增强组件的实际导入成本，不把构建产物总大小当作每个使用场景的成本。

SSR 的模块加载阶段不应执行 Canvas 创建和尺寸测量；客户端增强逻辑使用清晰入口。另设严格内容安全策略的测试页面，验证位移图使用的 data/blob URL、内联样式与 SVG 引用方式，并记录接入要求，不要求应用直接关闭安全策略。

## 8. 两个必须明确的技术边界

### 8.1 浏览器能折射背景，不代表 JavaScript 能读取背景像素

`backdrop-filter` 由浏览器负责处理元素后面的图像，这与把最终背景像素公开给业务 JavaScript 是两回事。标准 Canvas 输入与跨来源读取规则，也没有提供任意页面合成结果的通用自动采样接口。[^14][^15]

因此，以下实现思路不应直接写进产品承诺：通过 `getComputedStyle()` 知道真实背景亮度；依靠 `mix-blend-mode: difference` 保证所有文字合格；无条件读取任意跨来源媒体并实时计算对比度。

推荐三层策略：业务已知背景时提供 `backdropTone`；业务控制且允许读取的媒体可以考虑低分辨率采样；未知或高复杂度背景启用保守底色，必要时切换不透明表面。

这是一项有意识的能力边界，不是用一个 `autoContrast` 属性掩盖未解决问题。

### 8.2 堆叠上下文不等于背景采样边界

祖先的透明度、滤镜、遮罩、混合等属性，可能改变背景滤镜的处理边界；`transform` 或 `z-index` 的影响又不能简单等同于这些边界。CSSWG 对 Backdrop Root 的说明仍带有草案与待讨论性质，需要结合实际 Chrome 行为验证。[^14]

建议建立包含以下布局的固定回归场景：祖先 opacity 动画、带 filter 的容器、带遮罩的滚动区域、嵌套表面，以及通过 Portal 挂载的弹出层。

尤其不要盲目给所有组件添加 `will-change`、`isolation` 或 `contain: paint` 并宣称是通用优化。弹层的挂载位置也不是纯 z-index 问题，应与材质采样、裁剪和焦点管理一起设计。

## 9. 可读性、可访问性与 Chrome 支持策略

### 9.1 把可读性作为默认约束

WCAG 对普通文字通常要求至少 4.5:1 的对比度，大字通常为 3:1；关键非文本界面信息另有 3:1 的相关要求及适用例外。[^19][^20] 半透明组件需要检查实际合成背景，不能只比较 CSS 中两个声明的颜色。

建议使用白底、黑底、明暗交界、密集细线、正文、饱和色图片和动态视频作为背景压力场景。局部底色仍不能可靠保持可读时，直接增加不透明程度，而不是继续堆高光和文字阴影。

WCAG 2.2 AA 的目标尺寸条款以 24×24 CSS 像素为基本要求，并包含间距等例外；不能将 44×44 说成 AA 的统一最低门槛。[^21] 本项目可以把 40–44 CSS 像素作为常用桌面控制高度的设计起点，但这属于产品选择，应与密度和实际可点击区域一起定义。

### 9.2 用户偏好必须能够改变材质行为

Chrome 官方文档说明 `prefers-reduced-transparency` 可用于响应降低透明度的系统偏好，相关能力自 Chrome 118 起提供。[^22] 但具体系统如何暴露偏好仍需测试，因此组件库也应提供显式设置，不完全依赖系统开关。

建议的规则是：降低透明度时增加底色、减弱或关闭折射；减少动效时关闭弹性与追踪效果；高对比或强制颜色环境下优先保留系统颜色、边界和焦点。业务侧默认不得覆盖用户更保守的可访问性选择。

### 9.3 Chrome-only 的支持合同

建议在首个可发布版本中明确记录最低 Chrome 版本、已测试操作系统、硬件加速状态，以及移动端是否纳入承诺。

`CSS.supports()` 可用于属性和值的支持检测，但不能证明某个 `url(#filter)` 实际完成了预期位移，更不能证明效果可读或性能合格。[^28] 因此，本项目应通过自动化截图和真实交互测试验证渲染结果，而不是只验证 API 返回 true。

推荐保留三条路径：

```text
已验证的 SVG 增强
→ CSS 模糊材质
→ 稳定不透明表面
```

这不是为未支持的其他浏览器扩大范围，而是为 Chrome 内部的设备差异、用户设置和回归风险提供可用性保障。透明模式失效时，组件不应变得不可见或不可操作。

## 10. 性能预算与验收方法

### 10.1 不预先宣称哪种技术一定更快

CSS、SVG 和 GPU 渲染路径的实际成本需要在目标页面中测量，不能仅按 API 名称排序。常规动画应尽量避免反复触发布局和绘制，但 transform、opacity 的通用建议还要服从玻璃组件自身的背景采样约束。[^23]

建议首先减少同时存在的独立背景滤镜面积，复用分组表面，限制贴图分辨率，并避免每帧重新生成几何资源。

作为数量级理解，单张 RGBA8 图像的像素数据可近似计算为：

```text
内存字节数 ≈ CSS 宽 × CSS 高 × DPR² × 4
```

这只是单张图像、特定像素格式的算术估计，不是实际 GPU 总开销；中间缓冲、对齐、滤镜区域和多次处理都会影响真实用量。

### 10.2 建议的测试矩阵

| 维度 | 建议测试项 |
| --- | --- |
| 背景 | 静态图片、滚动正文、细线网格、视频、明暗变化背景。 |
| 表面 | 单个控件、多个独立表面、共享工具栏、大弹层。 |
| 交互 | 点击、键盘切换、拖动、滚动、开关弹层、连续改变窗口尺寸。 |
| 显示 | 不同窗口尺寸、DPR、浏览器缩放和系统缩放。 |
| 设备 | 至少覆盖目标范围内的集成显卡设备与 Apple GPU 设备；宣称支持的平台均应有对应样本。 |
| 生命周期 | 重复挂载卸载、路由切换、多实例、SSR hydration。 |

记录完整 Chrome 版本、操作系统、硬件和硬件加速状态。软件渲染或无头环境可以用于部分回归，不应被包装为真实用户 GPU 性能结论。

60 Hz 一帧约为 16.7 ms，120 Hz 一帧约为 8.3 ms，这是帧预算的算术参考，不是本项目已经达到的指标。建议记录掉帧、帧时间分布、主线程工作，以及绘制和合成成本，而不是只看平均 FPS。

INP 的“良好”参考阈值是页面访问第 75 百分位不超过 200 ms，但 INP 关注点击、触摸和键盘等交互，不包含 hover、滚动本身。它不能替代玻璃跟随和拖动流畅性的测试。[^24]

### 10.3 发布门槛

建议把“发布时必须满足”定义为：完整键盘操作和焦点行为通过；标准背景集合中的关键文字保持可读；CSS 和不透明路径可用；重复挂载无明显资源持续增长；在已声明设备上达到项目实际测得并公开的交互预算。

Playwright 可使用正式 Chrome 对应的 channel；仅测试其默认捆绑 Chromium，不应等同于已经完成 Google Chrome 产品测试。[^25]

静态视觉回归固定背景和动画状态，动态过渡另做交互测试。自动可访问性检查应与人工检查结合，尤其关注复杂背景上的透明文本、中文长标签、200% 缩放和焦点轮廓。

## 11. 分阶段路线与验证门槛

| 阶段 | 主要产出 | 进入下一阶段的条件 |
| --- | --- | --- |
| P0：材质概念验证 | 同一场景下比较 CSS 基线、现有内核与自研小原型；建立背景压力测试台。 | 折射确实可见，前景不失真；已知布局边界；成本在目标设备上可接受。 |
| P1：最小组件系统 | Provider、Surface、按钮、工具栏、选择控件和弹出层；完成 token 与状态规则。 | 可以组成完整界面；不需要每个组件独立调滤镜；键盘行为和可读性通过。 |
| P2：动态与组合 | 滑块活动透镜、共享位置过渡、ScrollEdge、密度与更多场景。 | 新效果没有破坏默认稳定性，并可被减少动效或透明度策略关闭。 |
| P3：工程化发布 | SSR、主题、文档、测试、版本策略、包体分析和分发机制。 | 支持范围、已知限制、迁移方式与性能测量条件均明确。 |

**P0 的停止条件同样重要。** 如果 SVG 在目标布局下不稳定，或成本明显超出可接受范围，应让 CSS 材质成为正式默认，将 SVG 留作受控增强，而不是为追求折射拖住所有组件。

产品验证建议邀请一小批目标开发者完成真实接入任务，例如把现有媒体工具栏替换成该库，或为工作区加入一个命令弹层。可以先用 5–8 位参与者发现问题；这是建议的探索样本，不是统计代表性声明。

观察首次可用组件的接入步骤、需要修改的 token 数量、布局冲突、复杂背景失败次数，以及接入者是否愿意在第二个页面继续使用。不要仅以 GitHub stars 或单张演示的反响判断产品成立。

## 12. 风险、命名与许可

| 风险 | 早期信号 | 推荐应对 |
| --- | --- | --- |
| 过度玻璃化 | 层级难分、信息密度下降、所有区域都在吸引注意 | 限定功能层，提供普通内容表面的搭配规则。 |
| 可读性不稳定 | 换一张背景或滚动到某段正文后文字消失 | 限制 clear 使用，加入保守底色和不透明策略。 |
| 性能失控 | 多实例和大面积滤镜下明显掉帧 | 共享表面、限制资源尺寸，按实测提供质量档位。 |
| 浏览器合成问题 | 父元素动画或 Portal 改动后折射突然消失 | 建立布局回归集合，记录限制，不靠随机增加 CSS 属性修补。 |
| 对竞品重复建设 | 核心卖点只是相同容器与参数 | 优先复用内核，将投入转向规范、场景、质量和开发体验。 |
| 宣传超出能力 | 宣称原生实现、自动合格对比度或全设备高帧率 | 使用明确的近似、支持范围和实测条件说明。 |

建议使用独立品牌名，说明设计灵感来自 Apple Liquid Glass，不暗示官方授权、合作或背书。Apple 的商标与版权使用指导应纳入命名和宣传审核。[^26]

Apple 字体下载不等于获得任意 Web 字体再分发许可；应核对具体字体许可，不将 SF 字体直接打包到组件库。系统字体栈与具有合适许可的替代字体更适合作为默认方案。[^27]

图标、截图、壁纸和演示媒体也要分别核查许可。参考开源代码时保留相应版权与许可说明；演示站避免直接搬运整套 Apple 产品素材。这部分是发布风险提示，不替代具体法律审查。

## 13. 最终建议与立即行动项

建议按以下顺序推进，而不是先列出几十个组件名称：

1. **建立对照实验台。** 用同一组背景和形状比较 CSS 基础材质、rdev、Liqui Design 与最小自研原型，判断是否确有必要自研内核。
2. **确定默认设计语言。** 先冻结 regular、clear 的使用边界，以及 compact、comfortable 两类几何规则；透明度和动效控制同时进入基础设计。
3. **做一个完整场景。** 以媒体查看器的工具栏、导航和弹出层为第一条闭环，并加入普通滚动正文作为反例测试。
4. **先验证质量，再扩展目录。** 完成真实 Chrome 的可读性、键盘、SSR、布局与性能测试，随后再加入滑块、融合动画和源码 registry。

**最终推荐：以 CSS + SVG 为可验证的材质路线，以 Base UI 或 Radix 为交互基础，以“内容清晰、操作层有玻璃感”为默认设计原则，构建一个克制而完整的 React 组件系统。**

项目最值得投入的部分，不是让某个矩形更像玻璃，而是让同一套组件在不同背景、尺寸、状态和输入方式下，仍然像同一个经过设计的产品。
