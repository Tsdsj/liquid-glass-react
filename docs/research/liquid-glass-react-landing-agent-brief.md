# Liquid Glass React｜Landing Page 评估与实施建议

## 01  文档说明与核心结论

文档版本：1.0  ｜  整理日期：2026-09-20  ｜  状态：设计建议稿，待本地仓库核验

适用对象：读取本项目代码的本地 AGENT，以及负责页面设计、前端实现和验收的开发者。Markdown 是便于机器读取的主版本；Word 与其使用同一份正文内容。

> 推荐方向：新增一个独立、浅色、克制、以真实交互为中心的产品首页。先让访客操作一个漂亮的小应用，再说明这些体验如何用你的 React 组件搭建。不是把文档首页装饰得更像玻璃，也不是制作满屏透明卡片的特效页。

### 1.1  产品定位与访问路径

建议定位：面向内容型应用与交互工具的 Liquid Glass React 组件系统。首页应传达“清晰、轻盈、真正好操作的 React 界面”，而不仅是“复刻了某种玻璃效果”。

主访问路径：认识产品 → 亲手体验 → 看懂用途 → 开始接入 → 确认边界。首页负责建立理解与兴趣；文档负责提供安装、API 和问题答案。

### 1.2  本文的证据边界

本文件整理自本次对话中的上一份评估报告。本轮未重新抓取网站、核验远程仓库或执行测试；原报告未取得完整线上渲染截图，也未进行实机性能测试。因此，本文不构成最新版本审计、视觉验收或生产可用性认证。

“原报告观察”是上轮报告对源码与文档的描述，须由 AGENT 在本地复核；“设计建议”是推荐方案；“实施与验收建议”是为交接补充的执行依据，不表示用户已经批准所有改造。仓库事实优先于本文对文件路径、API、依赖和测试数量的描述。

## 02  现状评估与本地核验

### 2.1  应保留并放大的资产

| 原报告观察（待复核） | 设计价值与处理建议 |
| --- | --- |
| 内容层保持实色；玻璃主要用于导航、控件与浮层。[S02] | 保留“内容稳定、操作悬浮”的系统性。不要让新首页把所有表面玻璃化。 |
| 已有 MediaViewer，串联场景、收藏、显示、菜单与导出等交互。[S03] | 优先改造现有小应用，把真实组合体验作为首页核心，而非重新制作无业务含义的组件拼盘。 |
| 可拖动的分段控件、开关、滑杆是项目特点。[S02] | 用可见反馈证明交互质量，减少仅靠宣传文案说明“流畅”的做法。 |
| 已有原创湖泊山脉 SVG 场景及冷暖变化。[S08] | 保留自有视觉资产。背景提供材质参照，不需要依赖 Apple 壁纸建立识别。 |

### 2.2  首页目前的主要问题

原报告描述：现有首页依次放置标题、入口、数字信息、媒体演示、设计原则和能力边界；同时复用文档侧栏或窄屏底部标签栏。[S06][S07] 这适合文档概览，但产品体验出现得偏后，首次访问者容易先进入“查文档”心态。

原报告还指出：折射演示默认关闭；音量滑杆位于设置浮层中，但动态背景没有音轨。[S03][S06] 首页建议保留库的保守默认，只对局部展台做受控增强，并把演示滑杆改为缩放等可立即看见结果的操作。

## 03  视觉方向与信息架构

> 视觉主张：浅色展厅，真实界面。页面是安静的展示空间，组件才是产品。清晰的内容、少量悬浮的玻璃、直接可操作的控件，共同建立辨识度。

### 3.1  建议视觉参数

| 项目 | 第一版设计建议 |
| --- | --- |
| 页面底色 | 冷调浅灰 #EDF0F4，避免整页高亮纯白。 |
| 内容表面 / 主文字 | 实色面板 #F6F7FA；主文字 #171B24，不使用透明或渐变正文。 |
| 品牌强调色 | 克制的蓝色 #265DDB，集中用于主操作，不让每个控件争抢注意。 |
| 玻璃位置 | 顶部导航、展台工具栏、局部控件、菜单和弹出面板。 |
| 布局 / 标题 | 桌面内容宽约 1120–1200px；标题约 56–72px；移动端约 36–44px。 |
| 圆角 / 层次 | 展台与面板用圆角矩形；按钮、分段控件才使用胶囊形。阴影服务于层级。 |

以上是起始参数，不是已验证的配色标准。实施时接入现有语义 token，在实际背景、状态和字号下检查可读性。不要另建一套与组件库脱节的首页皮肤。

### 3.2  五段式页面结构

| 页面段落 | 访客问题 | 主要内容 / 出口 |
| --- | --- | --- |
| 01 Hero 与主展台 | 这是什么？有什么不同？ | 明确定位 + 真实小应用；开始使用 / 体验组件。 |
| 02 材质与交互体验 | 效果有什么差异？ | 同场景材质比较；可拖动控件与可见结果。 |
| 03 组合场景 | 能用来做什么？ | 媒体与画廊、阅读与收藏、偏好与设置。 |
| 04 开发者接入 | 如何放进我的项目？ | 最小代码、实时预览、安装、对应源码。 |
| 05 能力边界与收尾 | 我需要注意什么？ | 兼容与验证说明；文档、更新日志、GitHub。 |

### 3.3  替代方向与取舍

深色沉浸式路线更容易形成强烈视觉，但也容易让项目被理解为装饰特效库；极简开发者路线信息直接，但不容易在第一眼传达材质与交互差异。推荐浅色产品展台，同时吸收极简开发者路线的信息清晰度。

不推荐作为默认方案：黑底紫色光晕、无限漂浮、满屏透明卡片、所有内容都使用玻璃、滚动劫持或重型视差。它们会削弱本项目清晰、克制、系统化的定位。

## 04  首屏设计与主展台

### 4.1  首屏文案与入口

| 位置 | 推荐文案 / 行为 |
| --- | --- |
| 品牌与定位 | Liquid Glass React / 为 React 构建的 Liquid Glass 组件系统 |
| 主标题 | 让界面轻盈，让交互有感。 |
| 副标题 | 可拖动的控件、克制的材质分层、按需开启的边缘折射。 |
| 主 CTA | 开始使用 → 安装指南。必须有唯一明确的主操作。 |
| 次 CTA / 顶部导航 | 体验组件 → 本页体验区；组件、文档、GitHub、外观设置放在导航。 |
| 展台提示 | 真实 React 组件，试着拖动下面的控件。 |

### 4.2  结构线框（文本示意，不是最终像素稿）

```text
[品牌]                  [组件] [文档] [GitHub] [外观]

             为 React 构建的 Liquid Glass 组件系统
                   让界面轻盈，让交互有感。
               [开始使用]       [体验组件 ↓]
                  [安装命令，支持复制]

          [原创背景 + 可直接操作的媒体 / 画廊展台]
             [场景] [显示模式] [缩放] [收藏] [… ]
              真实 React 组件，试着拖动控件。
```

### 4.3  交互应有立即可见的结果

| 操作 | 可见结果 |
| --- | --- |
| 场景切换 | 背景变化，同时呈现玻璃在不同内容之上的表现。 |
| 缩放滑杆 | 直接改变画面缩放，替代没有音轨反馈的音量示例。 |
| 分段控件 | 切换真实显示模式，同时可体验点击与拖动。 |
| 收藏 / 更多 | 状态明确改变，或打开可使用的菜单、浮层。 |

布局验收建议：在 1440×900 桌面视口、100% 缩放下，无需滚动即可看到并操作主展台的重要控件。优先减少标题和留白占用，不以固定高度裁切文本换取首屏露出。

增强策略：组件库默认行为保持不变；首页仅在经过验证且可用的环境中，对一小块展台使用增强折射，并提供清楚的材质切换与回退状态。背景不能喧宾夺主。

## 05  材质比较与组合场景

### 5.1  第二段：看起来是玻璃，用起来是界面

使用紧凑的交互体验区，而不是参数调试面板。访客应通过两次以内的简单操作，理解材质差异和控件反馈；这一操作数量是设计目标，不是已经测得的用户研究结果。

| 模块 | 设计与行为 |
| --- | --- |
| 材质模式 | 同一场景中切换“不透明 / 磨砂 / 边缘折射”。三种模式属于首页比较方案，不代表库已提供三个同名 API。 |
| 比较控制 | 保持背景、组件尺寸、位置与文案一致，仅改变材质呈现。避免用不同背景制造不可比较的视觉差异。 |
| 能力状态 | 边缘折射不可用时显示明确状态并回退，不提供没有效果的假开关。具体检测方式沿用并核实项目实现。 |
| 控件任务 | 分段控件控制视图；开关控制网格辅助线；滑杆控制缩放。每个控件只配一句简短操作提示。 |
| 展示密度 | 只提供理解价值最高的控制项；完整 API、参数和高级配置仍在文档中。 |

### 5.2  第三段：证明它是一套系统

不要铺满所有组件，也不使用自动滚动组件墙。通过三个实色场景卡片，或一个支持标签切换的共享展台，展示同一套语言如何处理不同任务。

| 场景 | 展示重点 | 希望传达的能力 |
| --- | --- | --- |
| 媒体与画廊 | 工具栏、菜单、显示控制 | 玻璃作为内容之上的操作层。 |
| 阅读与收藏 | 清晰文字、列表、导航 | 不使用玻璃的内容区域也有完整设计。 |
| 偏好与设置 | 输入、开关、滑杆、浮层 | 组件能组成真正的操作流程，而不只是截图。 |

首版可先完成媒体与画廊，再补阅读与设置。若采用共享容器，同一时刻只运行当前场景，避免为一排展示卡同时维持多个复杂演示。场景切换时保证尺寸稳定，不使页面反复跳动。

### 5.3  组件真实性原则

> 所有展示中的按钮、菜单、输入和浮层都应使用库的真实组件、真实导出与合理配置。背景插画和页面排版可以定制，但不要给组件加上下游用户无法复现的“首页特供”视觉修补。

可复现性是组件库官网与普通品牌官网的重要区别。若某种展示需要新增组件能力，应单独说明，而不是把一个页面局部实现包装成已有公共能力。

## 07  响应式、交互与质量边界

### 7.1  动效与材质

页面静止时保持安静，动效集中于按压、拖动、切换和打开浮层。避免满屏鼠标追光、每张卡片三维倾斜、无限漂浮、滚动劫持。减少动效设置不仅作用于库组件，也应覆盖首页新增的背景和装饰动画。

不要为展示效果修改库的默认材质行为。优先沿用现有能力检测与回退路径；只有核实可用时才开启局部增强。折射不可用或主动关闭时，页面仍应完整、可读、可操作。

### 7.2  移动端与缩放

| 场景 | 建议验收行为 |
| --- | --- |
| 窄屏布局 | 使用简短顶部导航。标题、安装命令、预览纵向排列；将低频操作收进菜单。 |
| 交互提示 | 不依赖 hover 才显示关键说明；触摸可操作，不能只有桌面鼠标效果。 |
| 内容适配 | 不靠固定高度裁掉放大后的文字；避免页面级横向溢出。代码区可以独立横向滚动。 |
| 测试范围 | 以 Chrome 桌面和 Chrome 窄屏 / 触摸模拟为主。模拟结果不等于真机验证，更不等于 Safari 兼容结论。 |

### 7.3  键盘与无障碍（实施补充建议）

交互控件具有可理解的名称、可见焦点与正确状态。分段控件和滑杆不能把拖动作为唯一操作方式，应保留适合其语义的键盘及非拖动操作。菜单 / 对话框支持合理的焦点进入、退出与恢复；关闭行为遵循所用组件模式。

对实际背景上的文字、边框和焦点进行可读性检查。透明材质不应让正文或关键状态难以分辨；不可把自动化通过表述成完成所有无障碍验证。

### 7.4  性能与测量

控制同时运行的复杂场景数量；离屏或非当前场景停止不必要的动画、计时器或渲染。先保证一个展台的体验，再决定是否需要额外特效或依赖。

不要在未测量时宣称“稳定 60 FPS”或固定倍数性能差异。若对外展示性能数据，应记录设备、Chrome 版本、视口、启用效果、测量方法和结果；未覆盖的环境明确标注。

此次工作不主动扩大为全浏览器适配或库级重构。其他浏览器沿用现有回退策略；兼容性文案只能覆盖实际验证范围。

## 08  工程组织与路由方案

### 8.1  新增首页，不重写文档

原报告描述站点使用 Vite 和 hash 路由，空路径进入概览，文档页面统一置于 Shell 内。实施前需核对真实入口、路由分发、站点 base 和主题挂载位置。[S07][S10][S11] 不要为一个首页迁移整个框架。

| 目标入口 | 建议行为 |
| --- | --- |
| 无 hash 的站点入口 | 显示新的 Landing Page，使用独立 LandingShell。 |
