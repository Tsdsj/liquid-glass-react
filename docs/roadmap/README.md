# 路线图

每个版本一个目录，目录名就是版本号。属于哪个版本的计划，就放进哪个目录。

| 版本 | 状态 | 目录 |
| --- | --- | --- |
| 0.0.1 | **已发布** 2026-09-16（npm `latest`） | 无。它早于这套格式，记录在 [`../action-items.md`](../action-items.md) 与 [`../../CHANGELOG.md`](../../CHANGELOG.md) |
| **0.0.2** | **开发中，未发布** | [`0.0.2/`](0.0.2/) — 第一阶段已交付，第二阶段进行中 |
| 0.3.0 | 未开始 | [`0.3.0/`](0.3.0/) |
| 0.4.0 | 未开始 | [`0.4.0/`](0.4.0/) |

## 版本号规则

这套规则是为了让「这件事属于哪个版本」有唯一答案，而不是每次重新讨论。

| 版本段 | 收什么 | 判据 |
| --- | --- | --- |
| **0.0.x** | 纯新增与修复 | 装了上一个 0.0.x 的人升上来，**一行代码都不用改**。新增可选属性、新增组件、修 bug、文档站，都属于这里 |
| **0.3.0** | 第一个允许破坏的版本 | 改了已有类型的形状、改名、删除、改变既有行为。必须附改名对照表（`docs/migration-0.3.md`） |
| **0.4.0** | 0.3.0 装不下的 | 视 0.3.0 的反馈定 |

`0.1.0` 与 `0.2.0` **永久不可用**：这两个号被 2026 年 7 月的旧实现用掉了，npm 的版本号一次性使用，下架也不还号。所以 0.0.x 之后的下一个次版本号直接跳到 0.3.0。详见 [`../../RELEASING.md`](../../RELEASING.md)。

判一件事归哪里，只问一句：**它会让现有代码改吗？** 会 → 0.3.0；不会 → 0.0.x。「这是个大功能」不是理由，`SplitView` 是一整个布局容器，但它是纯新增，所以进 0.0.2。

## 这次归纳改正了什么

2026-09-20 把两份散在 `docs/` 根下的 roadmap 拆进版本目录。拆的过程发现六处版本号对不上，逐条记在这里，因为它们都曾经是「看起来对」的说法：

| # | 原来写的 | 实际 | 处理 |
| --- | --- | --- | --- |
| 1 | 文件名 `roadmap-0.3.md` | 它的标题是「0.0.2 → 0.3.0」，而且大半内容是 0.0.2 交付的 | 按版本拆成两份，各自进 `0.0.2/` 与 `0.3.0/` |
| 2 | 排期表「**0.0.2 已发布 2026-09-19**」 | **0.0.2 从未发布**。标签打过又删了，npm 上是 0.0.1 | 改成「开发中，未发布」 |
| 3 | 新组件第一批标着「（0.3.0）」 | 所有者 2026-09-20 决定移进 0.0.2 | 移进 `0.0.2/phase-2-plan.md` |
| 4 | `SplitView` 在「第二批（0.4.0）」 | 新计划把它放进 0.0.2 的布局线 | 以新计划为准，`0.4.0/plan.md` 里删掉 |
| 5 | 2.3 兼容性「A、B、C、**G** 都是纯新增，进 0.0.2」 | G 没做。它确实是纯新增，但第一阶段没排进去 | G 留在 0.0.2，移到第二阶段 |
| 6 | 「搜索建议」同时出现在 G（0.0.2）与 0.4.0 排期 | 它是 `SearchField` 的一个可选属性，纯新增 | 归 0.0.2 的 G，0.4.0 里删掉 |

## 写 roadmap 的约定

- **先证据，后计划。** 每一条先写为什么认为它是问题——来自代码行号、实测数字或 HIG 原文——再写要做什么。没有证据的只能列为「疑点」，不排期。
- **完成的不删，标注。** 交付之后在原条目上标「已完成」并写清落在哪个文件，原始证据留着。删掉就没人知道当初为什么做。
- **一件事只属于一个版本。** 跨版本的计划要拆，不要一份文档写两个版本。
